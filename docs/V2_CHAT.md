# Чат клиента и мастера — план v2

Добавлено 4 октября 2026 по прямому запросу пользователя. **Запланировано, не реализовано и не опубликовано.** Очередь реализации: `V2_NEXT_IMPLEMENTATION.md`.

## Согласованная цель

Клиенту нужен простой способ уточнить услугу или попросить изменить пожелания перед её оказанием; мастер должен видеть и отвечать на эти вопросы на площадке. Приоритет — минимум действий, особенно на телефоне. Обычная гостевая запись остаётся доступной без регистрации и без обязательной переписки.

## Простой первый сценарий для реализации

- Из карточки существующей записи — действие «Написать мастеру» для клиента и открытие той же переписки у мастера. Вверху контекст визита: услуга, дата/время и исполнитель. Диалог сохраняется после обновления страницы.
- Текстовое сообщение, отправка, понятная ошибка с повтором без потери текста и счётчик непрочитанного. Повторная отправка одного запроса не создаёт дубликат.
- Сообщения помогают договориться; цена, длительность, время и статус не меняются автоматически по тексту. Любое изменение визита проходит календарь, проверку пересечений и предусмотренное подтверждение новых условий.
- Вложения/расширенные уведомления рассмотреть отдельным следующим шагом при подтверждённой потребности. Наличие технического канала уведомления не считать готовностью настоящей доставки.

## До кода определить детали

1. Нужна ли переписка ещё **до создания записи** через страницу мастера или достаточно начать с существующего визита.
2. Как гость получает подтверждённый приватный доступ к диалогу без усложнения гостевой записи; существующую личную ссылку визита нельзя автоматически расширять до доступа к любой переписке.
3. Кто отвечает за салон: назначенный мастер, владелец либо оба с явно определёнными правами. Для сотрудника без аккаунта не создавать автоматически фиктивный логин; выбрать понятного ответственного.
4. Как сохраняется доступ и история при переназначении визита, отзыве доступа сотрудника или архивировании. Новый мастер не должен автоматически читать посторонние разговоры клиента.

Это вопросы следующего этапа проектирования, не уже согласованные решения.

## Защита и границы

- Сервер проверяет участника при списке/чтении/отправке каждого диалога. Публичный slug, ID записи или знание имени клиента не дают доступ. Права сотрудников ограничены соответствующим визитом/диалогом, роль владельца описывается явно.
- Аккаунт использует существующую защищённую сессию; provider secrets и токены не выдаются через сообщения, публичный API или браузерное хранилище. Гостевой доступ, если выбран, должен быть ограничен конкретным диалогом, с проверкой и отзывом права.
- Текст выводится без исполнения HTML; проверяются размер/частота сообщений, повтор запросов и корректный источник отправки. Тела переписки и контакты не попадают в публичные ответы, диагностические логи или архив выпуска.
- На новой базе предусмотреть участников, сообщения, автора, порядок, отметку прочтения и связь с записью; точную схему выбирать после решения доступа гостей/салона. Не добавлять таблицы в production только ради фиксации плана.

## Приёмка

Проверить мобильный путь клиент → мастер → ответ, сохранение после перезагрузки, непрочитанные, ошибку/повтор без дубля и попытки доступа постороннего по ID. Отдельно проверить гостя, салонного сотрудника/владельца, отзыв/архив/переназначение, текст с HTML и неизменность условий/занятости визита при обычном сообщении. Ключи и приватные сообщения отсутствуют в публичных ресурсах. Простой сценарий бронирования без регистрации сохраняется.
