# Карта, адреса и рост v2

4 октября 2026. Только v2. Текущий релиз `20261004-v2-map-card`; выпуск, сохранность данных и публичный браузер подтверждены в `RELEASE_20261004.md`, история viewport — `RELEASE_20261003.md`. Ниже механизм и границы проведённых проверок. Рабочая база пока SQLite, переход на PostgreSQL/PostGIS не выполнен.

## Адрес: согласованный простой сценарий

В настройках индивидуального мастера и салона два поля — **«Город»**, **«Улица и дом»** — и отдельная кнопка **«Сохранить»**. После нажатия показывается успех или ошибка. Подсказок при наборе, поясняющего блока, внешнего брендинга, ссылки на карту и ручного выбора точки в нынешней форме нет.

Сервер проверяет конкретный населённый пункт, улицу, дом и корпус/строение через DaData; строгий резервный геокодер может уточнить точную точку. Для нового адреса требуются существующий дом и точные координаты. Центр города, улица или ближайший дом не подставляются. Неоднозначный адрес, отсутствие точной точки, сбой/лимит провайдера возвращают ошибку; прежний адрес сохраняется. Ключ провайдера хранится только на сервере. Адресная кнопка меняет адресные поля; «Сохранить страницу» использует ранее сохранённый адрес.

Действующие сохранённые адреса не удаляются. Старые API ручной точки/подсказок оставлены для совместимости прежних открытых клиентов; новая форма их не вызывает. Предыдущие предложения автодополнения и ручной карты заменены последним решением пользователя. Подробности реализации/защиты: [V2_ADDRESSES.md](V2_ADDRESSES.md).

## Что реализовано для карты

Leaflet/OpenStreetMap остаются отображением карты, SQLite — источником данных площадки. Новый `GET /api/map/viewport` используется текущим `frontend/src/pages/Map.tsx`; прежний `/api/map/masters` сохранён для совместимости.

| Возможность | Текущий механизм |
| --- | --- |
| Выбор видимой области | Клиент отправляет bbox, zoom, поисковую строку и направление. После первоначального поиска карта подстраивается под найденные границы; перемещение дальше загружает выбранную область |
| Пространственный индекс | Производная `map_locations` хранит публичные места, SQLite RTree `map_spatial` выбирает пересекающиеся точки. Точные координаты дополнительно сверяются с bbox, поскольку RTree расширяет float32 границы |
| Обновление опубликованных точек | Триггеры профиля, сотрудника и workspace обновляют производную модель при обычных изменениях, включая записи из другого соединения SQLite. Источником остаются исходные страницы |
| Группы на общем виде | Сервер группирует точки по экранной сетке. На ответ не более **300 объектов карты** суммарно: одиночные точки и группы. При необходимости сетка укрупняется, количество исходных мест не обрезается |
| Полный счётчик | `total` — все подходящие места в области. `points.length + сумма clusters.count = total`. Старый предел 1 000 не используется в новой выдаче |
| Боковой список | По умолчанию **24 карточки**, API допускает 1–48. Кнопка «Показать ещё» использует cursor; страницы позволяют дойти до всех результатов, без дублей в клиенте |
| Совпадающие координаты | При нажатии группа приближает карту. На максимальном приближении либо при совпадении координат открывается список «В этом месте», из которого можно выбрать конкретного мастера/салон. Для возврата есть «Все в этой области» |
| Поиск и направления | Поиск по названию, городу, адресу и направлениям; кириллица без зависимости от регистра. Категории салона берутся у действующих доступных для записи сотрудников |
| Продвижение | Подготовлены выделение одиночных точек/групп, сортировка и маркировка; сохраняются те же bbox/категории/публичность. Продвижение остаётся **выключенным** (`PROMOTIONS_ENABLED=0`), новая карта его автоматически не включает |

В публичную модель попадают опубликованные действующие индивидуальные мастера без demo-флага в личном workspace с владельцем и опубликованные салоны с владельцем/координатами. Сотрудники салона не превращаются автоматически в дополнительные отдельные метки адреса салона. Персональные заметки, контакты гостей и служебные поля в карточки карты не входят.

Каждое чтение выполняется в одном SQLite snapshot: изменение публикации между выбором координат и карточек не должно выдавать частично согласованную страницу. Cursor/выбор группы подписаны сервером, ограничены сроком и текущими фильтрами/zoom/областью/размещениями; для времени также актуальной доступностью/минутой расчёта. Некорректный токен или смена запроса требуют обновления результата. В браузере отменяются устаревшие запросы и догрузка прежнего списка; выбранная карточка выводит пользовательский текст средствами React без HTML-вставки.

Viewport принимает bbox, zoom, q, category, limit, cursor, cluster и **soon=true**. «Есть время в ближайший час» означает: начало строго позже текущего времени, не позже чем через час, и вся реальная услуга помещается без пересечений визитов/перерывов в общем календаре человека. Для салона подходит хотя бы один действующий доступный сотрудник; время карточки отображается по часовому поясу места приёма. Одинаковые правила действуют на рекламные страницы. Проверка фактической занятости при записи остаётся обязательной независимо от результата поиска.

`GET /api/map/details?kind=master|salon&id=...&category=...` проверяет только выбранное публичное место, ближайшую полную услугу за 7 дней и реальную публичную обложку. Личные контакты/заметки и ключи не возвращаются. Общий дополнительный лимит 60 запросов свободного времени/карточки в минуту; ответы no-store. Браузер обновляет карточку и фильтр раз в минуту/при возвращении, отменяет прежний запрос при смене точки. Ссылка записи передаёт public ID услуги, время и сотрудника салона; календарь ещё раз загружает реальные окна.

В `lib/schedule.mjs` добавлено пакетное чтение расписаний, связанных исполнителей и занятых интервалов только внутри текущего snapshot. Стартовые окна рассчитываются существующим алгоритмом записи. Кеш между запросами отсутствует, интервалы чтения включают полную максимальную длительность услуги после конца окна поиска. Обычная карта не рассчитывает календари всех профилей.

## Проверки и измеренная скорость

Источники: `lib/map-viewport.mjs`, `tests/map-viewport.test.mjs`, `scripts/benchmark-map.mjs`, локальный отчёт `.cache/map-viewport-benchmark.json`. Проверки покрывают полные счётчики/все страницы на 1 100 анкетах, совпадающие точки, публикацию/архив/адресные изменения, направления салона, рекламные токены и границы, некорректный ввод, пересечение линии смены даты, работу индекса, закрытый backup и повторный запуск миграции. Дополнительно проверяется публичный HTTP API настоящей схемы v2.

Локальный benchmark: Node v22.22.2, синтетическая изолированная in-memory SQLite, пять прогревочных и 60 измеряемых чтений на сценарий. Ни сеть/HTTP, ни отрисовка/панорамирование телефона, ни параллельные записи в измерение не входят. p95 — время вычисления одного ответа `map.read`, размеры — сериализованный JSON.

| Сценарий | Точек | p95, мс | Объектов карты | Карточек в ответе | JSON, байт |
| --- | ---: | ---: | ---: | ---: | ---: |
| Город, zoom 11 | 1 000 | 10,39 | 8 | 24 | 10 194 |
| Город, zoom 18 | 1 000 | 18,58 | 135 | 24 | 54 822 |
| Поиск по городу и направлению | 1 000 | 21,22 | 24 | 24 | 15 903 |
| Город, zoom 11 | 10 000 | 106,06 | 12 | 24 | 11 660 |
| Город, zoom 18 | 10 000 | 265,08 | 96 | 24 | 41 898 |
| Небольшая область улицы, 676 результатов | 10 000 всего | 12,23 | 84 | 24 | 37 048 |
| Поиск по всему городу и направлению | 10 000 | **474,17** | 96 | 24 | 41 898 |

Пространственный план использует RTree. Число маркеров и размер списка ограничены, результаты сохранены полностью. При этом **474 мс p95 локального поиска по всему городу** остаются конкретным ограничением: внутри широкого bbox сервер ещё читает/фильтрует/сортирует все подходящие позиции и вычисляет группы в JavaScript; синхронный SQLite занимает процесс на время запроса. Это не доказательство готовности к массовым одновременным поискам или отсутствия задержек на мобильном устройстве.

Следующие измерения — тот же набор в отдельной тестовой базе на сервере, несколько одновременных поисков и запись в календарь, HTTP p95/таймауты, мобильное панорамирование и объём памяти. Само присутствие 1 000 мастеров не является порогом обязательной миграции базы.

### Измерение фильтра ближайшего часа — 4 октября

Для `soon=true`: 1 000 синтетических мастеров≈104 мс, 10 000≈1 017 мс (до пакетного чтения≈2 448 мс). Без фильтра соответственно≈20/127 мс и **0 расчётов календаря**. Источник `.cache/benchmark-map-soon.mjs`, `.cache/map-soon-batch.json`; одна реальная 30-минутная услуга и суточный график на мастера, SQLite в памяти. Это по одному локальному прогону, **не p95 и не конкурентная нагрузка**. Синхронный расчёт большого города остаётся риском для одновременных поисков; следующие проверки выполняются на отдельной PostgreSQL/PostGIS и закрытой тестовой базе, без изменения рабочей базы.

## Подготовка PostgreSQL/PostGIS

Готов [V2_POSTGRES_MIGRATION.md](V2_POSTGRES_MIGRATION.md) с инвентаризацией текущих таблиц, SQL/transaction различий, безопасным переключением и ограничениями общей занятости человека в личной практике/салоне.

Добавлен `scripts/sqlite-migration-snapshot.mjs`: приватный согласованный экспорт исходных таблиц, PK/FK/индексов/порядка, 64-битных значений, BLOB и контрольных сумм; проверка целостности, адресных координат и общих пересечений визитов. Пять тестов прошли, включая закрытую настоящую схему текущего приложения и Windows ACL. `map_locations`, RTree и три shadow tables только инвентаризируются: в PostgreSQL производный индекс будет создан из исходных данных. Снимки с аккаунтами/контактами/хешами не публикуются и не входят в архив приложения.

**PostgreSQL не подключён, pg-адаптер и импортёр не реализованы, данные площадки не перенесены.** Подготовленный экспорт не подтверждает возможность восстановления PostgreSQL. Нужны отдельная закрытая база, законченные миграции/адаптер, импорт актуального backup и сверка всех данных, тест гонок общей занятости, проверка восстановления и измеренное окно запрета записи.

Целевая модель: точка WGS84 `geometry(Point,4326)` и GiST для области. Радиус в метрах — geography с соответствующим индексом; [PostGIS ST_DWithin](https://postgis.net/docs/ST_DWithin.html) различает единицы geometry/geography и поддерживает индексный предварительный отбор. Полный OpenStreetMap в базу площадки импортировать не требуется; картографическая подложка остаётся отдельной.

PostGIS ускоряет пространственный поиск, но не проверяет текст адреса и не определяет свободное время. Для широкого городского поиска дополнительно нужны индексируемый текстовый фильтр и уменьшение объёма группировки/сортировки в приложении. Обновление базы само по себе не отменяет эти измеренные затраты.

Перенос должен сохранить ID/слуги, связи пользователей и performer, календари/историю, приглашения, гостевые ссылки, адреса и фотографии. Переход выполняется после репетиции на закрытой актуальной копии; две независимые рабочие базы с расходящимися визитами не допускаются. После новых записей в PostgreSQL возврат к старой SQLite требует сначала сохранить и перенести эти новые данные.
