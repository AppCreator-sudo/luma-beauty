Это постоянный контекст и рабочая инструкция; актуальные даты и статусы находятся в [PROJECT_ROADMAP.md](<../../PROJECT_ROADMAP.md>), непосредственная точка продолжения — в верхнем блоке [WORK_CHECKPOINT.md](<../../WORK_CHECKPOINT.md>).

## 1. Как пользователю начать новый чат

Создавать чат внутри проекта **pwa**, привязанного к `C:/Users/Admin/Desktop/pwa`. В корне расположен [AGENTS.md](<../../../AGENTS.md>), который направляет агента к этим документам. Достаточно написать:

> Продолжай по плану проекта.

Агент должен самостоятельно прочитать документы, назвать текущий этап и начать первую доступную задачу. Для отдельной задачи достаточно её названия, например «работаем над картой»; заново объяснять площадку не нужно.

Новый чат должен видеть именно папку проекта. В этой рабочей копии на 10 октября нет `.git`, поэтому запуск из `frontend/` вместо корня может не обнаружить корневые инструкции. Использовать корень `pwa`; создавать Git-репозиторий ради этой инструкции не требуется.

Если агент не подхватил контекст, короткая резервная команда:

> Прочитай AGENTS.md в корне pwa и продолжи с верхнего блока docs/WORK_CHECKPOINT.md.

Это файловая передача контекста, а не автоматическое чтение всех прежних переписок. Официальный механизм описан в [документации OpenAI об AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md). Новый чат или повторный запуск нужен, чтобы заново подхватить изменённые инструкции; загрузка в отдельном новом чате ещё не проверена этой сессией.

## 2. Что мы строим

**Luma Beauty** — российская бьюти-площадка: мастера и салоны, портфолио работ, поиск и карта, запись клиента, управление услугами, графиком и визитами. Ранее проект назывался «Ателье» / Atelie; старые названия в путях, пакетах и серверной службе не означают другой продукт.

Цель пользователя — довести площадку до очень качественного приложения с выразительной подачей для женской аудитории и простыми рабочими инструментами профессионалов. Приоритет сейчас: **перенос утверждённого UI, затем завершение остальных функций**. Не подменять этот этап новой архитектурой или случайными украшениями.

Рабочий сайт: https://atelie-13-143-66-1.sslip.io/v2/ . Постоянный домен пользователь купит отдельно. Упоминания текущего выпуска в документах — последняя подтверждённая запись, а не проверка сервера в реальном времени.

## 3. Пользователи и продуктовые границы

| Участник | Сценарий и ограничения |
| --- | --- |
| Гость / клиент | Просматривает работы и специалистов; записывается через услугу → мастера → время → контакт. Гостевая запись не должна требовать обязательного аккаунта. Приватные сведения не показываются в каталоге. |
| Самостоятельный мастер | Имеет свою публичную страницу, портфолио, услуги, расписание и календарь. В кабинете — заявки, записи, оформление и настройки. |
| Владелец салона | Управляет салоном и командой, услугами сотрудников, графиками, визитами, публикациями и архивом. Отображаемая подпись управляющего — **«Менеджер»**; технически это существующая роль владельца. |
| Сотрудник салона | Карточка и портфолио находятся внутри салона. Создание сотрудника не требует его аккаунта. Старые связи аккаунтов/данные сохраняются; новые приглашения к самостоятельному управлению не возвращать без согласования. |

В общем каталоге — салоны и самостоятельные мастера с равным визуальным статусом. Не показывать отдельно каждого сотрудника салона. У салона команда доступна внутри публичной страницы и записи.

Для готовой карточки сотрудника нужны фото, имя, направления и явно сохранённый график; для онлайн-записи также назначенная услуга с ценой/длительностью и рабочий интервал. Черновик скрыт. Скрытие сохраняет записи; архивирование отдельно проверяет будущие визиты. Восстановление не включает запись автоматически.

Публикации создаются общей формой с адресатом салон/конкретный сотрудник. Работы мастера связаны с его услугой; салон может публиковать интерьер/атмосферу либо новости. Нельзя терять автора при фильтрации или записи.

## 6. Как агент выбирает задачу данного чата

1. Выполнить конкретное поручение пользователя, если оно есть. Запрос документации означает только документацию; не возобновлять остановленную реализацию.
2. При продолжении прочитать верх checkpoint. Не выбирать следующий этап по старой переписке, названию чата или старому `ROADMAP.md`.
3. Найти ID задачи, статус, зависимости и критерии в [PROJECT_ROADMAP.md](<../../PROJECT_ROADMAP.md>).
4. Проверить существующий код. «Ещё не перенесён новый UI» не означает «функция отсутствует».
5. Если задача уже выполнена другим чатом — сверить файлы/свежий checkpoint, не повторять. Если обнаружен конфликт актуальных документов, исправить статус по проверяемым фактам; спорное продуктовое решение обсудить.
6. Одним коротким сообщением назвать выбранную работу, например: «Начинаю U-08: сверку действующей записи и подготовку недостающих состояний макета». Продолжать самостоятельную работу в согласованных границах только после нового запроса пользователя возобновить работу; остановку из актуального checkpoint соблюдать.
7. Если этап слишком велик для одной сессии, закончить связный сценарий и записать точное оставшееся место, файлы, проверки и ограничения. Частичный UI не публиковать как завершённый этап.

Если одновременно работают два чата в одной папке, не назначать им одну задачу и одни файлы. Проверить свежие записи о текущей работе; при обнаруженной коллизии согласовать разделение, а не перезаписывать изменения. Не создавать другие чаты или агентов без соответствующего запроса/инструкции.

## 7. Как проверять и публиковать

Каждый UI-этап: сравнить реализацию с утверждённым изображением при сопоставимом viewport, проверить desktop/mobile, длинные тексты/пустые состояния, прокрутку и уменьшение движения. Затем сборка и целевой сценарий. Для данных — сохранение/reload и отказ чужому пользователю; для записи — правильные мастер/услуга/время; для карты — синхронизация точек и списка.

Рабочая карта сейчас Leaflet/OpenStreetMap; адресный механизм сохраняется до отдельного утверждённого изменения. PostgreSQL/PostGIS ещё не подключены. Смена этих технологий не является частью переноса UI.

Разрешение пользователя на проверенные UI-выпуски зафиксировано в [плане UI](<../../V2_UI_REFERENCE_IMPLEMENTATION.md>). Перед каждым выпуском убедиться, что оно действует для этой задачи, и проверить фактический серверный release. Подготовить резервную копию и откат, загрузить только нужные файлы, сохранить shared/data/uploads, проверить HTTP/assets/health/service. Не перезапускать backend ради статических файлов без причины. Отдельные рискованные миграции не покрыты разрешением на UI.

Сбой инструментов фиксировать точной ошибкой; не выдавать предположение за причину и не менять конфигурацию Codex без задачи. Не останавливать посторонние процессы.

## 9. Источники истины и их приоритет

Последнее прямое решение пользователя → актуальный checkpoint и датированный статус → утверждённые макеты/уточнения → профильная спецификация → код и результаты проверки конкретной функции. Старые документы нужны для истории и отдельных неизменённых требований, но не заменяют новую очередь. Расхождение между кодом и утверждённым требованием отметить как задачу, а не автоматически отменять требование.

`ROADMAP.md`, `V2_PRIORITIES.md`, `IMPLEMENTATION_PLAN_2026-09-24.md`, старые концепты и выпускные отчёты не задают текущий порядок. Подробный план переноса — `V2_UI_REFERENCE_IMPLEMENTATION.md`; оперативная очередь — `V2_NEXT_IMPLEMENTATION.md`; сводный датированный реестр — `PROJECT_ROADMAP.md`.
