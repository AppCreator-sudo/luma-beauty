## Серверная подготовка — результаты этапа 3 октября 2026

- Общий серверный вход через Яндекс, VK ID и Telegram; выбор нового кабинета и возврат к приглашению сохраняются на сервере. Повторный вход находит аккаунт по идентификатору провайдера, без создания дубля.
- Раздел «Доступ к аккаунту» для всех ролей: привязка дополнительного провайдера, подтверждение недавнего входа перед привязкой, завершение остальных сессий. Существующие аккаунты не объединяются автоматически. Нельзя заменить уже привязанный аккаунт провайдера или присоединить чужую идентичность.
- В подготовке 3 октября отображение внешних способов зависело от настроенных провайдеров. Опубликованный экран `/v2/auth` теперь использует безусловно отключённые кнопки «Скоро» из U-07N; прежнее описание не является инструкцией включить их по env. Парольный вход сохраняется до настоящей проверки внешнего входа и переноса пользователей без потери доступа.

## Защита и границы проверки

- Секреты приложения и обмен кода на токены — на сервере. Токены провайдеров не сохраняются в браузере или базе; постоянная связь содержит только provider/subject/user_id.
- Состояние входа одноразовое, хранится по хешу, привязано к cookie браузера. PKCE verifier хранится на сервере; ошибки и отмена возвращаются без сырых ответов провайдера. Приватная ссылка приглашения остаётся во фрагменте URL.
- Сессии HttpOnly, Secure при HTTPS, SameSite=Lax; срок 30 дней. Привязка требует подтверждения входа не старше 10 минут и той же действующей сессии до и после обмена с провайдером. Старые сессии требуют подтверждения.
- VK: конфиденциальное Web-приложение, серверный service_token, разрешённый исходящий IP сервера; проверяются state, device_id и совпадение user_id. Минимальный scope vkid.personal_info.
- Telegram: OIDC Authorization Code + PKCE, Client ID/Client Secret из Login Widget, не токен бота. Подпись ID token проверяется по фиксированному JWKS, RS256, issuer/audience/срок/возраст. Если nonce присутствует, проверяется совпадение; отсутствие nonce разрешено в потоке кода, привязанном через PKCE и одноразовое state.
- Не выполнены реальный вход у внешних провайдеров, привязка на опубликованном домене, аудит всего приложения или гарантия отсутствия уязвимостей. Общий публичный сайт после выпуска проверен, но это не проверка внешней авторизации.

## Настройка после выбора домена

1. Выбрать постоянный HTTPS-домен, настроить его на сайте и APP_ORIGIN.
2. Яндекс: приложение Yandex ID, callback `/auth/yandex/callback`, серверные YANDEX_CLIENT_ID/YANDEX_CLIENT_SECRET.
3. VK: пользователь подтвердил профиль VK Бизнес; само приложение ещё не создано. Конфиденциальное Web-приложение, callback `/auth/vk/callback`, разрешённый исходящий IP, VK_CLIENT_ID/VK_SERVICE_TOKEN.
4. Telegram: создать бота в BotFather и настроить Login Widget: origin и `/auth/telegram/callback`, RS256. TELEGRAM_CLIENT_ID/TELEGRAM_CLIENT_SECRET.
5. Секреты вводить в закрытую серверную конфигурацию, не в переписку, клиентские переменные или публичные файлы. `.env.example` содержит только пустые образцы.
6. Проверить настоящий вход, отмену, повторный вход, роли, совместимость уже существующих приглашений/связей и привязку второго провайдера. Новые приглашения сотрудников не возвращать в рамках настройки входа. Отдельно согласовать и реализовать включение внешних действий в UI; только после проверки доступа существующих пользователей решать вопрос парольной формы.
