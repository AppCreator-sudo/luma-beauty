## Назначение и меню

Клиент быстро находит следующий визит, понимает его статус, возвращается к понравившимся работам/мастерам и управляет личным доступом. У клиента нет профессионального календаря, графика работы, услуг или редактирования салона.

Утверждённые разделы: **Обзор / Мои записи / Сохранённое / Мои мастера / Отзывы / Уведомления / Настройки**. Desktop — зелёная шапка с утверждённым логотипом/веткой, sidebar на всю высоту и молочная рабочая область. Mobile — та же шапка, доступ к разделам через общее пружинное меню; нижних пунктов не будет согласно новому требованию. Без дублирования desktop-sidebar. Форма входа сохраняет целевой экран.

Постоянные полезные действия: найти мастера/салон, открыть вдохновение, открыть карту. Не превращать обзор в подборку рекламных баннеров. Кнопка «Новая запись» ведёт в каталог, а не создаёт визит напрямую.

## Предложенный набор в исходной сверке

### 1. Обзор

- Ближайший активный визит: дата/местное время и часовой пояс, услуга, реальный исполнитель, салон при наличии, длительность, зафиксированная цена, статус, адрес, «Открыть запись».
- Если заявка pending: «Ожидает подтверждения»; не выдавать её за подтверждённый визит. Подтверждённые и ожидающие не объединять без статуса. При отсутствии ближайшего визита — компактное приглашение найти мастера.
- Следующие 2–3 записи; «Все записи». Напоминание об отзыве только для собственного done без отзыва.
- 4 сохранённые работы, короткий список мастеров; новые пользователи получают действия, а не искусственные цифры/образцы.
- Одна компактная полоса состояния уведомлений. Без числовых KPI, дохода, календаря работы и больших пустых колонок.

### 2. Мои записи и детали

- Вкладки **Предстоящие / История**, статусы и временная сортировка; отменённые и завершённые различимы. Пагинация/дозагрузка при большом количестве, состояние актуализации данных.
- Детали: клиент, услуга, исполнитель/салон, дата/время/часовой пояс, продолжительность, цена визита, адрес на момент записи, ориентир к карте, статус, комментарий, выбранная работа при наличии.
- Действия по статусу: pending/confirmed — отменить с подтверждением; done — оставить/посмотреть отзыв и записаться снова; cancelled — записаться снова. Просроченный confirmed сам по себе не становится done: завершает мастер/владелец.
- При повторе заново проверить публикацию/услугу/цену/расписание и показать актуальные условия в стандартной форме. Не обещать старую цену и не резервировать слот до заявки.
- Адрес подтверждённого визита должен браться из данных визита; текущий authenticated /appointments не возвращает полный адрес/город, нужно расширить ответ без чужих контактов. Скрытый/архивный специалист остаётся в истории; нельзя терять старую запись или вести на сломанную ссылку.
- Комментарий клиента и внутренние заметки управляющего не смешивать. Сейчас поле notes общее: перед выводом «Ваш комментарий» определить отдельные поля/источник; чужие внутренние заметки не показывать клиенту.
- «Добавить в календарь» — экспорт .ics по выбору клиента, с корректным часовым поясом; нового серверного календаря не требуется. «На карте» — существующая карта/точный адрес с текущим провайдером.
- **Перенос утверждён 11 октября:** запрос нового времени с подтверждением мастера/владельца. Исходная запись действует до принятия; при принятии атомарно проверить свободное окно. Это новая серверная функция, текущий клиентский PATCH перенос не поддерживает. До её реализации кнопку не выводить.

### 3. Гостевые записи

- Простой сценарий «Есть запись без аккаунта?» → открыть/вставить свою секретную ссылку → увидеть детали → подтвердить добавление в кабинет.
- Добавляется только визит, подтверждённый секретным ключом. Не привязывать по одинаковому номеру, имени, Telegram или логину провайдера.
- Обязательно проверить уже привязанный чужому аккаунту визит, повтор своего claim и отменённый визит. Сейчас accessible() уже отклоняет любой привязанный визит и ключ старше 90 дней после окончания: чужой визит нельзя присвоить. Для повторного открытия собственной ссылки нужен понятный переход в существующую запись/идемпотентный ответ; проверку владельца не ослаблять. Истёкшую ссылку не выдавать за импортируемую.
- Секретный ключ не попадает в аналитику/логи/поиск; из адресной строки /visit он не передаётся серверу как URL-параметр. Не выводить полный ключ в карточках списка.

### 4. Сохранённое и мои мастера

- Сохранённые работы: Pinterest-подобная сетка 4 desktop / 2 mobile, автор, салон для сотрудника, услуга при наличии, удаление из сохранённого, правильная запись по работе. Не терять performer_id/salon_service_id.
- Мои мастера: компактные карточки подписок самостоятельных мастеров, категория/город, открыть страницу, записаться, отписаться.
- Сохранение салонов — отдельная F-07; **в первом кабинете не рисовать работающую вкладку любимых салонов**, пока backend не реализован и UI отдельно не согласован. Сотрудники не получают отдельные общие карточки.
- Коллекции/доски, общие списки по ссылке и рекомендации по поведению — возможное развитие после базового кабинета; для запуска не нужны.

### 5. Отзывы

- «Можно оценить» / «Мои отзывы»; рейтинг/текст/дата/услуга/исполнитель. Создание по завершённому собственному визиту, без анонимных отзывов и повторов.
- Не давать оценивать салон целиком до F-07. Визит к сотруднику сохраняет авторство сотрудника/салон как контекст, а не создаёт произвольный общий рейтинг.
- Редактирование/удаление опубликованного отзыва сейчас не поддерживаются: отдельно обсудить правила и API. В основном макете только «Посмотреть отзыв».

### 6. Уведомления

- Предлагается компактный **центр событий**: подтверждение, изменение времени/услуги, отмена, напоминание, приглашение оставить отзыв. Прочитано/непрочитано, открытие связанной записи, без контактов на публичном экране.
- Это новая модель/endpoint: сейчас push не хранится как постоянный inbox. Сохранять событие на сервере и показывать его независимо от того, разрешены ли push.
- Push на конкретном устройстве: включить/выключить, доступно/запрещено/не поддерживается, тест. Напоминание за час соответствует текущей реализации; выбор «за день/за 2 часа» не добавлять до настройки реального планировщика.
- Новости платформы/маркетинговые рассылки выключены по умолчанию и не смешиваются с событиями записи. Не рисовать такие переключатели, пока нет отправки и согласованных правил.

### 7. Настройки и доступ

- Предлагаемые необязательные личные данные: имя для заполнения заявки, круглый аватар, предпочтительный контакт, город поиска. Сейчас User хранит только id/login/account_type: нужен отдельный приватный клиентский профиль; не переиспользовать публичный profiles мастера.
- Фото необязательно: по умолчанию инициалы. Допустимость файлов — общие правила avatar в lib/image-rules.json. Имя/контакт можно исправить в конкретной заявке; изменения профиля не меняют историю прошлых визитов.
- Контакт используется только при явной отправке записи. Не считать ввод телефона/Telegram проверенным способом входа. Не получать чужие визиты по совпавшему контакту.
- «Вход и безопасность»: смена пароля/восстановление, подготовленные Яндекс/VK/Telegram показываются по фактической доступности, выход на других устройствах/здесь. Не добавлять фиктивный список устройств: его API сейчас нет.
- «Мои данные»: экспорт собственных данных и запрос удаления аккаунта предлагаются перед публичным запуском. Удаление требует подтверждения доступа и согласованных правил активных визитов/анонимизации истории; текущего API нет. Не удалять записи мастеров целиком вместе с клиентским аккаунтом.
- Помощь — инструкции по записи/отмене/секретной ссылке и сообщению об ошибке. Канал поддержки согласовать отдельно; не придумывать чат с живым оператором.
