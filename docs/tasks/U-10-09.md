4. Записать согласование/локальную готовность/проверки/публикацию отдельно; обновить общий реестр.

## Приёмка

- Старый привязанный аккаунт/ссылка не теряет визиты/занятость/права; владелец сохраняет управление.
- Недостающий UI согласован; новые роли/приглашения/фиктивные аккаунты не создаются.
- Нет нижней панели/overflow/наложений, круглые аватары, действия от 44 px; целевая браузерная проверка важнее одной сборки.
- Перед изменением сверить утверждённые ссылки из UI-журнала. Missing/conflicting элементы сначала обсуждаются. На изменение UI: frontend/root build и целевой браузерный проход; на данные: save/reload/права на отдельной базе.

## Уточнение по аудиту U-10-01 — 15.10.2026

Первая гипотеза старой карточки об общей нижней панели уже снята U-10-14. Остаток — реальные ветки старых связей:

- WorkspaceCabinet/PerformerCabinet для уже связанного staff: календарь, свои услуги/график/работы/оформление; запрет чтения/изменения другого сотрудника, смена workspace, отозванная/архивная связь, reload и переход из /studio,/calendar,/me для account_type client/master.
- Shell выбирает standalone по account_type/наличию любого owner workspace, SalonPage — по выбранному workspace; проверить смешанный owner+staff и несколько memberships отдельно.
- **Приглашения отключены намеренно:** invitation() в lib/workspaces.mjs безусловно отвечает 410. Любой /join#fragment, включая старый формально неистёкший токен, должен показывать объяснение и Back/выход. Auth/accept в Join.tsx существуют в коде, но при текущем API недостижимы. Успешное принятие/выпуск новых ссылок не включать в приёмку и не восстанавливать ради BUG-003.

Создать только изолированные синтетические старые связи; пользовательские токены не извлекать. Облик наследует R10; при недостающей композиции сначала review, конкретное предложение есть в матрице.
