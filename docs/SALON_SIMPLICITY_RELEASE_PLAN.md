# Простой салон — подготовка выпуска

Это план выпуска U-10-20/21/22, **не подтверждение публикации**. Реализация разрешена пользователем 15.10.2026; рабочая миграция и новый выпуск требуют прямого поручения. Следующая карточка: [U-10-23](tasks/U-10-23.md).

## Состав

Единый прайс салона, назначения и индивидуальные условия; направления сотрудников из назначений; разделы «Услуги», «Мастера», «Календарь / Записи / Рабочие графики»; контекстные ссылки на работы; компактные native select. Публичная запись и карта используют активные предложения и фактические условия исполнителя. Гостевая заявка передаёт выбранное предложение и показанные цену/длительность; изменение условий требует нового выбора.

Миграция `salon-service-catalog-v1` добавляет четыре таблицы: `salon_service_catalog`, `salon_service_assignments`, `salon_service_aliases`, `salon_service_preserved_directions`. Таблица `services` остаётся с прежними пятью колонками и IDs. Снятие назначения и архив не удаляют исторические строки. Объединяются только точные совпадения названия/направления/цены/длительности; разные прежние условия остаются отдельными услугами с отметкой проверки. Старые ссылки принимаются через aliases. Независимые мастера не переходят на салонный каталог.

## Перед рабочим выпуском

1. Получить прямое поручение на публикацию. Проверить фактический серверный release/current и отсутствие другого выпуска. Последний известный на начало реализации — `20261015-v2-master-portfolio` (проверен 19:29:25+07); это не доказательство текущей версии на момент будущего выпуска.
2. Сделать свежий согласованный snapshot рабочей БД и сохранить shared uploads/config. Секреты и снимки не выводить и не добавлять в открытые отчёты. На отдельной копии выполнить `node scripts/verify-salon-catalog-migration.mjs <snapshot.sqlite> <private-report.json>`; проверить существующие строки, FK/integrity, точные группы, услуги с `needs_review`, старые ссылки и приватный backup. Проверить текущие данные до переключения; тестовую БД не переносить на сервер.
3. Собрать frontend и root, упаковать проверенные `server.mjs`, `lib/`, собранный `public/v2`, изменённый SW по обычному процессу проекта. Изолированно проверить запуск пакета. Подготовить проверяемый manifest/hash и фактический release ID, без выдуманных дат.
4. На короткое окно остановки сохранить закрытый backup; переключить весь проверенный пакет с сохранением `shared/data/uploads`. При старте миграция сама создаёт закрытый `VACUUM INTO` backup в `DATA_DIR/migration-backups` и отчёт счётчиков. Не накатывать отдельно frontend поверх старого API.
5. Проверить службу/health, версию bundle/SW, FK/integrity, сохранность прежних данных/media, GET публичных страниц/карты и реальное отображение кабинета. Не создавать вымышленные визиты или услуги в production ради проверки. Создать `RELEASE_YYYYMMDD_*.md` только после фактического выпуска.
6. По поручению пользователя синхронизировать private GitHub с понятным комментарием, подтвердить remote SHA. Отдельно зафиксировать публикацию и GitHub; push не доказывает работу сайта.

## Откат

До открытия нового выпуска для записей/редактирования допустим совместный откат кода и закрытого снимка, сделанного в остановку. Сохранить shared uploads; проверить целостность и прежний release.

После появления новых рабочих записей/изменений **не восстанавливать старый снимок поверх них**. Старый код не учитывает неактивные назначения и может снова предлагать снятые услуги. Один `current → старый release` после такого изменения недостаточен. Сохранить новую БД и журнал, временно остановить приём запросов, подготовить совместимое исправление вперёд либо отдельно проверенный обратный переход с сохранением новых записей. Такой переход пока не реализован и не разрешён автоматически.

Старые правила сменных графиков также сохраняются: старый код без schedule-patterns не должен снова открыть выходные. Не удалять новые таблицы и не пересоздавать услуги с другими IDs ради отката.
