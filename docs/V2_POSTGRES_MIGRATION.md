**Статус по документам на 11 октября 2026: подготовка, миграция не выполнена.** Рабочая площадка продолжает использовать SQLite; Leaflet/OpenStreetMap сохраняются. Последний подтверждённый выпуск — [U-08C r2](RELEASE_20261011_CLIENT_CABINET_REFERENCE.md), `20261011-v2-client-cabinet-reference-r2`, 11.10.2026 23:15:02 Новосибирск. Этот выпуск добавил клиентскую схему SQLite; данные и результаты экспорта 3 октября не описывают нынешнюю схему целиком. Перед репетицией F-03 нужна свежая закрытая копия и новая инвентаризация. Очередь — [карточки задач](tasks/README.md); переключение production требует отдельного разрешения.

PostGIS предназначен для хранения и поиска геоданных площадки; полный импорт OpenStreetMap не требуется. Новый UI карты U-09 не включает смену базы или провайдера.

## Подготовка и проверки инструмента — 3 октября 2026

- Добавлен операторский инструмент `scripts/sqlite-migration-snapshot.mjs`: согласованный экспорт всех исходных таблиц SQLite, их колонок, первичных/внешних ключей, индексов, представлений и триггеров. Исходная база открывается с `readOnly: true`, данные/проверки читаются внутри одной транзакции. Приложение и его автоматические миграции не запускаются.
- NDJSON хранит все значения, включая SQL NULL, 64-битные целые, BLOB и Unicode. Скрытый `rowid` сохраняется отдельно: нынешний порядок выбранных направлений зависит от него. Количество строк и SHA-256 есть для каждой таблицы; `manifest.json` записывается последним и обозначает завершённый экспорт.
- Снимок содержит приватные данные, включая хеши паролей, сессий, контакты и временные подтверждения. Вывод в терминал содержит только числа. Каталог обязан быть новым, его родитель должен существовать; публичные каталоги проекта, frontend, зависимости и deploy запрещены. На Linux — каталог 0700 и файлы 0600; на Windows — ACL без наследования, только текущий пользователь и SYSTEM. При ошибке настройки прав данные не записываются. Ключи окружения, VAPID и файлы загрузок не экспортируются.
- `readiness.json` включает `integrity_check`, внешние связи, NULL в первичных ключах, значения флагов, координаты, время/статусы визитов, JSON дней работы и пересечения активных записей одного человека, включая разные карточки салона и личную практику. Нарушения фиксируются, исходные данные не исправляются. Пропущенные проверки делают `dataChecksPassed` ложным.
- Производные `map_locations`, RTree `map_spatial` и его shadow tables `map_spatial_node`, `map_spatial_rowid`, `map_spatial_parent` инвентаризируются с числом строк/DDL/ключами, но помечаются `inventory-only-derived` без файлов данных. Они пересоздаются из profiles/performers/workspaces, их SQLite-хранилище не переносится в PostgreSQL. Связанные триггеры также помечены как производные. Проверяется ожидаемая схема RTree и map_locations; прочие virtual tables останавливают экспорт для ручной проверки. В summary `rows` — строки исходных таблиц, `derivedRows` и `derivedTables` — отдельная инвентаризация индекса.
- Пять тестов `tests/sqlite-migration-snapshot.test.mjs` прошли в этапе 3 октября, включая фактическую проверку Windows ACL, неизменность SQLite, большие числа/BLOB, составные ключи, порядок направлений, общие пересечения, повреждённые FK, изменение снимка и allowlist RTree. Отдельный тест создавал **настоящую схему через изолированный server.mjs того этапа**, регистрировал тестового мастера/владельца, создавал сотрудника без аккаунта, приглашение и визит; после остановки процесса экспортировал и сверял закрытую базу, включая performer FK. PostgreSQL, PostGIS, `psql`, Docker и импорт в PostgreSQL в этой проверке не запускались. Эти результаты не подтверждают новый прогон на схеме U-08C.

`dataChecksPassed: true` означает только прохождение перечисленных проверок данных. Это не подтверждение скорости, наличия всех бизнес-ограничений, исправности PostgreSQL или готовности к переключению сервиса. Контрольные суммы защищают от случайного повреждения; они не являются цифровой подписью против оператора, имеющего доступ ко всем файлам.

## Использование закрытого снимка

Node.js версии проекта (22.13+). Вначале создать закрытый родительский каталог оператора. Выбрать новый каталог назначения за пределами каталогов, доступных веб-серверу.

```powershell
node scripts/sqlite-migration-snapshot.mjs export --db .cache/closed-copy/atelie.sqlite --out .cache/closed-copy/pg-snapshot-20261003
node scripts/sqlite-migration-snapshot.mjs verify --dir .cache/closed-copy/pg-snapshot-20261003
node --test tests/sqlite-migration-snapshot.test.mjs
```

Операторский пример для закрытого backup после выпуска карты (каталог назначения ещё не должен существовать):

```sh
node /opt/atelie/current/scripts/sqlite-migration-snapshot.mjs export --db /opt/atelie/backups/20261003-v2-map-viewport/atelie.sqlite --out /opt/atelie/backups/20261003-v2-map-viewport/postgres-preparation
node /opt/atelie/current/scripts/sqlite-migration-snapshot.mjs verify --dir /opt/atelie/backups/20261003-v2-map-viewport/postgres-preparation
```

3 октября 2026 эти команды выполнены на закрытой предрелизной рабочей копии: 30 исходных таблиц, 76 строк; `dataChecksPassed: true`, `verified: true`. Каталог 0700, manifest и файлы 0600. Публикация карты также прошла репетицию производного индекса на другой закрытой копии с совпадением бизнес-хэшей; 5 производных таблиц проверены после миграции. Подробности: [выпуск 3 октября](RELEASE_20261003.md). **Эти числа исторические: их нельзя использовать как ожидаемое количество таблиц/строк актуальной базы или критерий её сверки.** Это не импорт и не проверка восстановления PostgreSQL.

На рабочем сервере инструмент допустимо запускать оператору на согласованной резервной копии в `/opt/atelie/backups/...`, с каталогом за пределами текущего release/public и shared/uploads. Не скачивать такой снимок в публичную папку и не включать его в архив приложения. Проверка `verify` не восстанавливает базу; она сверяет формат, типы, ширину строк, количество и контрольные суммы. Незавершённый каталог без manifest не используется. Нужен отдельный проверенный импортёр и проверка восстановления полного приложения с загрузками и закрытым окружением.

Инструмент не делает побайтовую копию `*.sqlite`: он экспортирует согласованные логические данные. Если источник работает в WAL, SQLite может использовать служебный `-shm`; рабочие SQL-данные инструмент не изменяет. Для операционной репетиции предпочтительна уже созданная согласованная резервная копия.

## Какие изменения нужны в сервере

| Сейчас | Необходимая адаптация |
| --- | --- |
| Синхронный `node:sqlite`, `.prepare().all/get/run`, общий db | Асинхронный слой хранения; явные методы доменов; запросы через PostgreSQL pool, транзакция через один полученный client |
| `?`, динамическое `IN (?,...)` | `$1…$n` и массивы `= ANY($n::text[])`; параметры остаются параметрами, пользователь не задаёт SQL/идентификаторы |
| `BEGIN IMMEDIATE` и синхронные callback-транзакции | `BEGIN/COMMIT/ROLLBACK`, блокировки общих ресурсов календаря, ограничения пересечений, повтор допустимых serialization/deadlock ошибок; нельзя разносить транзакцию по pool.query |
| `INSERT OR IGNORE`, `MAX(next_at,?)`, `PRAGMA`, реконструкция таблиц | `ON CONFLICT DO NOTHING`, `GREATEST`, отдельные версионируемые PostgreSQL-миграции, без автоматического ALTER при каждом старте |
| `ORDER BY rowid` в направлениях | Явная `position`; при импорте заполнять по сохранённому sqliteRowid. Составной PK `(performer_id,category)` сохранить |
| Флаги 0/1, даты в миллисекундах, JSON в TEXT | На первом переходе оставить флаги smallint с CHECK 0/1, epoch milliseconds bigint, JSON text с валидацией; изменение публичного API/типов выполнять отдельно |
| JS Number после чтения SQLite | PostgreSQL bigint/COUNT обычно приходит строкой: явные преобразования только в безопасном диапазоне, не глобальная потеря точности |
| SQLite lower/LIKE и JS Russian lowerCase, сортировка/cursor по slug | Определить стабильную нормализацию и collation для поиска/slug cursor; кириллица и одинаковый порядок должны пройти сравнение старого/нового API |
| COUNT/SUM/AVG, DISTINCT, `EXISTS` с целым результатом | Проверить типы результата и контракт API: bool, bigint, numeric/null. Избежать N+1 в каталоге/карте и подсчёте свободного времени |
| Сессии, OAuth и адресные доказательства в общей SQLite | Условное потребление через `DELETE … RETURNING`/`UPDATE … WHERE … RETURNING` внутри транзакции, сроки и связь с пользователем/сессией проверяются сервером |
| `address_budget` и `geocode_throttle` | Сохранить атомарные `RETURNING` и квоту; PostgreSQL shared rows должны координировать несколько процессов, не только in-memory лимит |

Предлагаемый клиент — `pg` с параметризованными запросами. Транзакции обязаны использовать один client, освобождаемый в finally; это требование [node-postgres](https://node-postgres.com/features/transactions). URL подключения хранится только в серверном закрытом окружении, не в frontend/снимке/logs. Runtime-роль не получает права создания расширений/миграций. Миграционная роль используется отдельно; база не открывается в интернет.

## Целевая география

В profiles/workspaces добавить `location geometry(Point,4326)` с GiST. Заполнять только из действующей пары longitude/latitude, порядок — **longitude первым**. Невалидные/односторонние пары блокируют импорт, NULL остаётся NULL. Не геокодировать историю заново при переносе.

Область карты выбирается через индексируемое пересечение с envelope; группы и пагинация сохраняют нынешние фильтры публикации, активного сотрудника, направления и доступности. Для поиска радиуса в метрах использовать geography и отдельный GiST индекс geography-выражения/колонки; [ST_DWithin](https://postgis.net/docs/ST_DWithin.html) различает единицы geometry и geography и использует предварительную индексную проверку. На geography не заменять радиус условием расстояния в градусах. Календарь остаётся отдельной задачей хранения, PostGIS адрес не подтверждает.

Рекомендуется одна общая read-модель публичных мест мастер/салон либо UNION ALL двух индексированных таблиц. Сотрудники салона не становятся отдельными метками адреса салона автоматически. Проверка адреса и точных координат продолжает выполняться сервером до сохранения.

## Защита общей занятости человека

Одного EXCLUDE по `master_id` недостаточно: личная и салонная карточки одного аккаунта имеют разные performer_id.

1. Создать постоянные `calendar_resources` и связь performer → resource. Для связанных карточек пользователя — общий ресурс человека; для сотрудника без аккаунта — самостоятельный ресурс. Ресурс не удалять вместе с отключением доступа/аккаунта, пока на него ссылается история.
2. В appointments добавить NOT NULL resource_id и FK; сохранить start/end в bigint миллисекундах. На каждый pending/confirmed резервировать полузакрытый интервал `[start,end)`; смежные визиты допускаются. Для text resource_id нужны операторы расширения btree_gist; диапазон — int8range. Предлагаемое ограничение: `EXCLUDE USING gist (resource_id WITH =, int8range(start,"end",'[)') WITH &&) WHERE (status IN ('pending','confirmed'))`, плюс `CHECK("end">start)`. Это проект ограничения, **SQL здесь не исполнялся**. [PostgreSQL range constraints](https://www.postgresql.org/docs/current/rangetypes.html#RANGETYPES-CONSTRAINT) описывает совмещение равенства ресурса и пересечения диапазонов.
3. Любая новая запись, перенос времени/мастера и подтверждение работает транзакционно. Сначала блокировать все затрагиваемые ресурсы в одном стабильном порядке, повторно проверять права, рабочие часы и состояние услуги, потом писать запись. EXCLUDE служит последним запретом гонки, SQLSTATE 23P01 возвращает обычную ошибку «время занято».
4. Принятие приглашения, отзыв доступа и смена связи пользователя с сотрудником должны менять ресурсы и активные записи **в той же транзакции** под теми же блокировками. Воссоединение карточек при пересечении не проходит. При отзыве доступа явно повторить текущую семантику разделения календарей; не оставлять занятость человека привязанной к чужому кабинету случайно.
5. Архив не удаляет визиты и не освобождает предстоящие записи молча. Передача не меняет цену, услугу, время и booking_venues снимок, пока это не требуется отдельным пользовательским действием.

CHECK, читающий другие строки/таблицы, не подходит для общей занятости; PostgreSQL предлагает межстрочные UNIQUE/EXCLUDE/FK для таких гарантий. [Ограничения PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html). Отдельно проверить восстановление, отмену, интервалы на границе дня и общее время сотрудника в двух салонах.

Исторические записи со статусом confirmed могут уже пересекаться после старого объединения аккаунтов: текущий accept проверяет будущие визиты. Экспорт выявляет все активные пересечения. Импорт не должен отменять такие записи или менять статус самостоятельно; согласовать обработку истории перед включением EXCLUDE. Настоящие конфликты будущих визитов исправлять через обычный кабинет, сохраняя историю.

## Сроки и секреты при переносе

- Сохранить users/identities без объединения по имени/телефону. `provider,subject` уникальны; пользователь сохраняет свои роли/членство. Сессии — только хеши, expires/authenticated_at прежние. Cookies остаются HttpOnly/Secure/SameSite, серверные проверки Origin сохраняются.
- Приглашения и guest_bookings ссылки переносятся с прежними хешами и состоянием. Статус used_at и срок не продлевать. OAuth state/PKCE verifier и address_choices — краткоживущие секретные доказательства. Снимок их содержит для полноты; перед импортом выбрать и протестировать политику: перенос только ещё действующих значений либо завершение начатых действий с просьбой повторить. Это не удаление аккаунта или истории.
- Индексы по expires нужны для sessions, oauth_states, address_choices и кешей. Очищать по expiry батчами отдельной задачей; WHERE expires>serverTime всё равно проверяется при использовании. Не делать CHECK expires>now(): оно не заменяет истечение при чтении.
- Загрузки, добавленный U-08C каталог `private-client`, private VAPID и server env — отдельные закрытые резервные копии. Приватные клиентские аватары нельзя переносить в публичный uploads или выдавать без проверки владельца. Экспорт SQLite не является полным резервным копированием сервиса.

## Последовательность перехода и обязательные проверки

1. **Свежая закрытая копия.** Согласованная SQLite backup после U-08C, отдельные копии uploads и private-client, новый снимок данным инструментом, проверка контрольных сумм и бизнес-нарушений. Включить все добавленные таблицы/колонки/индексы; старые числа 3 октября не являются эталоном. Не использовать локальные демонстрационные данные как источник production.
2. **Новая тестовая база.** Выбрать поддерживаемые совместимые версии PostgreSQL/PostGIS, закрытые сетевые права, ограничения ресурсов/резервного копирования. Создать отдельные миграции для всех таблиц, FK/delete правил и индексов; pg/schema пока отсутствуют в текущем backend.
3. **Импортёр и сверка.** Строго декодировать v1, сохранять ID и значения. Загрузка родительских сущностей → зависимых таблиц либо контролируемые deferred FK. Проверить число и содержимое каждой строки/связи, порядок направлений/фото, все старые slugs и private ссылки. Кеши/секреты сравнить с выбранной политикой, не копировать произвольно.
4. **Адаптер сервера.** Перевести все читающие/пишущие маршруты и фоновые задачи на одну PostgreSQL базу. Полный комплект API tests + клиентская запись/гостевая ссылка/календарь/совместимость старых приглашений/архив, а также U-08C: приватный профиль и аватар, claim, перенос/решение/коллизия, inbox/read и экспорт. SQLite не остаётся вторым независимым писателем.
5. **Гонки и скорость.** 1 000/10 000 мест, фильтры и видимая область, индексы EXPLAIN ANALYZE, p95 и размер ответов. Одновременная запись/перенос/accept на общий ресурс из разных соединений — ровно один допустимый победитель, остальные 409 без потерянных изменений. Проверить лимит pool, таймауты и повтор deadlock/serialization.
6. **Репетиция выпуска.** Измерить длительность окна запрета записи, повторить финальный экспорт/импорт и восстановление PostgreSQL из backup. Проверить uploads, env, сервис и публичные read-only страницы. На старой базе до этого все записи продолжаются.
7. **Финальный переход.** На время согласованного короткого окна остановить все SQLite писатели, сделать новый backup, экспорт/импорт/сверку, атомарно переключить сервис. Возврат до открытия записи — на прежнюю SQLite и приложение. После первых новых PostgreSQL записей откат к старой SQLite **запрещён без переноса новых данных**: сначала закрыть запись и согласовать восстановление, иначе потеряются визиты.

Выпуск миграции допустим только после прохождения шагов 1–6 и отдельного отчёта о результатах. Нынешнее улучшение карты можно выпускать на SQLite независимо; оно не является свидетельством миграции PostgreSQL.
