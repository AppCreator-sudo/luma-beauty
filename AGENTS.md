# Luma Beauty — инструкции для чатов проекта pwa

Проект: бьюти-площадка Luma Beauty, ранее «Ателье» / Atelie. Рабочая папка `C:/Users/Admin/Desktop/pwa`. Разработка только v2: `frontend/`, `server.mjs`, `lib/`. `public/app.js` и старые экраны v1 не являются источником текущего UI.

В GitHub/Codex Cloud рабочая папка — корень checkout этого репозитория, а не Windows-путь выше. Все пути ниже относительны ему. Для cloud прочитай `docs/CODEX_CLOUD.md`: Node.js 22.22.2 (минимум 22.13), два `npm ci`, frontend/root build и `python3 scripts/validate-docs.py`; локальный запуск `npm start` с `NODE_ENV=development`, `DATA_DIR=.local-data/cloud`, подходящим `APP_ORIGIN` и URL `/v2/`. На Windows `npm.cmd`/`python`, на Linux `npm`/`python3`. По умолчанию production env/БД/ключи не копируются в разработку. Отдельное поручение OPS-04 от 14.10.2026 разрешает полную копию и отдельный доступ разработки/публикации: читать docs/CLOUD_SERVER_ACCESS.md. Передача зашифрована, ключ — в настройках выбранной Only me среды; plaintext в Git запрещён. Постоянные серверные права пока требуют дополнительного одобрения после отказа автоматической проверки. Для базового setup .env.example не применять автоматически, там серверные defaults. Доступ GitHub, публикация cloud-среды и production-выпуск — разные факты. Перенос/актуализация инструкции не разрешает исправлять код или тесты; найденное фиксировать отдельными открытыми задачами.

## Начало каждого нового чата

1. Прочитай `docs/NEW_CHAT_GUIDE.md` — контекст, роли, правила и алгоритм работы.
2. Прочитай **верхний актуальный блок** `docs/WORK_CHECKPOINT.md`, затем `docs/CURRENT_STATE.md`.
3. Открой единый список `docs/tasks/README.md`, выбранную карточку и её зависимости. Крупные этапы — `docs/PROJECT_ROADMAP.md`; для UI сверяй `docs/V2_UI_REFERENCE_IMPLEMENTATION.md`. `V2_NEXT_IMPLEMENTATION.md` — только указатель, не вторая очередь.
4. При «продолжай», «дальше по плану», «приступай» самостоятельно возьми первую незавершённую доступную задачу из checkpoint/плана. Кратко назови её и начинай работу; не проси повторить описание проекта. Если пользователь дал конкретную задачу, работай по ней. Открытие нового чата без запроса не означает разрешение на выпуск или выполнение всей очереди.
5. Если пользователь остановил работу, не продолжай разработку сам. Запрос только на документацию не отменяет остановку реализации. Новый явный запрос продолжить возобновляет работу.
6. До изменений прочитай код и навыки, перечисленные в карточке. Отметь статус и чат-исполнитель в карточке/`docs/tasks/registry.json`; не дублируй занятую задачу. `deferred` не брать в код, `blocked`/`awaiting_input` сначала разрешить по указанным условиям. Не сканируй весь проект и историю всех чатов без необходимости.

## Неизменные правила продукта и UI

- **Утверждённый UI = внешность реализации.** Эталоны — `docs/ui-concepts/2026-10-10-luma/` и утверждённые уточнения 10–11 октября; точные ссылки для экрана в `docs/V2_UI_REFERENCE_IMPLEMENTATION.md`. Не перезаписывай исходные PNG. Главная сохраняет опубликованную полноэкранную композицию.
- Недостающие функции/элементы, противоречия и отклонения от эталона сначала обсуждай с пользователем с конкретным вариантом решения. Исправление явного бага в уже согласованном UI не требует нового концепта.
- Салон и самостоятельный мастер равноправны в каталоге. Сотрудники находятся внутри салона, не отдельными карточками общего каталога. Салоном управляет владелец; «Менеджер» — подпись в UI, не новая серверная роль.
- Площадка не принимает оплату услуги между клиентом и мастером и не берёт комиссию за клиента/визит. Будущая монетизация продвижением — отдельное продуктовое решение, не разрешение встроить оплату записи.
- Сохраняй роли, текущие данные, гостевую запись, календарь, портфолио и остальные действующие функции. Фото/имя/категории/сохранённый график обязательны для готового сотрудника; для записи нужна услуга с ценой/длительностью.
- Desktop и mobile одного этапа выполняются вместе: без горизонтального переполнения и наложений, доступные действия от 44 px, круглые аватары, `prefers-reduced-motion`.
- Не вводи вымышленные бизнес-данные в production. Для тестов используй отдельную базу. Правила фото — `lib/image-rules.json`. Не добавляй платную DaData; не заменяй точный адрес соседним домом. Провайдер карты и база не меняются в рамках UI.

## Проверка и выпуск

- Frontend: `npm.cmd --prefix frontend run build`. Корневая проверка: `npm.cmd run build`. Тесты выбирай по изменению, например `node --test tests/appointment-editing.test.mjs`; не повторяй полный набор без причины.
- Проверяй изменённый сценарий в браузере; для данных — сохранение, reload и права. Сборка сама по себе не доказывает правильный внешний вид.
- Даты — `Asia/Novosibirsk`. Не придумывай сроки и даты реализации. Разделяй «согласовано», «сделано локально», «проверено», «опубликовано».
- Перед выпуском проверь фактическую серверную версию и действующее разрешение пользователя. Предыдущее разрешение на проверенные UI-выпуски записано в плане; отдельная новая смена архитектуры/данных им не разрешена. Сохраняй резервную копию и рабочие `shared/data/uploads`; локальные тестовые базы не отправляй на сервер. Не выводи секреты из конфигурации/SSH-файлов.

## Завершение каждого этапа

Обнови карточку и `docs/tasks/registry.json`, пересобери список командой `python -X utf8 docs/tasks/update-index.py`. Затем обнови `PROJECT_ROADMAP.md` (статус/фактические даты/проверки), `CURRENT_STATE.md` (короткая сводка), `WORK_CHECKPOINT.md` (точная следующая задача). Для UI обнови журнал `V2_UI_REFERENCE_IMPLEMENTATION.md`; при выпуске создай `RELEASE_YYYYMMDD_*.md` с версией и откатом. Незавершённые части и новые баги — отдельные открытые карточки. Запрос только на документацию не запускает реализацию и не требует сборки приложения: проверь ссылки, карточки, зависимости и сохранность эталонов. Не объявляй весь раздел завершённым по одной перенесённой форме.

Объясняй результаты по-русски, понятным языком: что изменилось, как проверено, что осталось. Пользователю не нужно разбираться в технических деталях, чтобы продолжать проект.
